SATISFIED 참조 문서를 실제로 열어 확인했다

Workflow Planning이 Functional·NFR·Infrastructure Design을 “기존 명세로 충족”으로 처리했으므로, 그 명세가 U2 범위에 충분한지 가정하지 않고 직접 대조했다. 05-portal-api.md(엔드포인트 13종·인증 매트릭스·오류 포맷), 04-db-schema.md(U1의 schema/sdlc.ts와 교차 확인 — 필요한 테이블이 전부 이미 있다), 08-sr-registration-ui.md, 03-state-machine.md §1.2 는 충분했다. 나머지 세 문서에서 아래 발견 사항이 나왔다.

F-1 · 이 승인이 결정하는 항목

Tailwind v4 + shadcn/ui가 도입되지 않았다

00-overview.md §6은 스타일링을 Tailwind CSS v4, 컴포넌트를 shadcn/ui로 못 박고 08-sr-registration-ui.md §9는 16종을 이름으로 지정한다. 그런데 U1이 만든 것은 순수 CSS이고 apps/portal/package.json에 Tailwind·Radix 의존이 없다. U2가 첫 UI 유닛이라 결정이 지금 내려진다.

A안 권장

명세대로 Tailwind v4 + shadcn/ui를 도입하되, @theme을 기존 tokens.css 변수에 연결한다. U1의 layout.css는 그대로 둔다.

근거 — ① requirements/가 SSOT이고 Q5=A(명세 우선)가 이미 확정됨 · ② 뒤따르는 3개 UI 유닛의 중복을 막는 판단은 U1에서 AuthGuard를 10함수로 넓힌 것과 같음 · ③ shadcn은 파일 복사라 되돌리기 쉬움

B안

U1의 순수 CSS를 이어가고 프리미티브를 손으로 작성한다.

대가 — 명세 §6 이탈이 확정된다. Dialog·Select의 접근성을 직접 책임져야 한다. 네 유닛이 각자 만든다.

이 계획을 승인하면 A안을 승인하는 것이다

B안을 원하면 승인 대신 그렇게 말해 달라. 결정을 뒤로 미루면 U4·U5·U6 착수 시점에 같은 질문이 세 번 더 나온다.

F-4 · 파급이 가장 넓은 발견

커버리지 게이트가 apps/를 재지 않는다

vitest.config.ts의 coverage.include는 packages/lib/src/**/*.ts 한 줄뿐이고, CI(ci.yml)는 그 설정 그대로 vitest run --coverage를 돌린다. U2 코드는 전부 apps/portal/src/**에 있으므로 집계에 한 줄도 들어가지 않는다.

나머지 발견 사항

소유자 없는 유틸, 낡은 문서, 되살리지 않을 범위

F-2 · 공유 유틸 2종에 소유자가 없다

U1이 secret_refs 테이블과 AuthError는 만들었지만, 그 표에 쓰는 코드는 만들지 않았다. AES-256-GCM 암·복호화(04-db-schema.md §8.1 · 01-auth-github.md §6)와 AuthError → §7 표준 오류 응답 매퍼가 없다. 방치하면 U2가 PAT·repo 파일·env var로, U6가 MCP 토큰으로 암호화를 각각 구현하고, 네 유닛의 라우트가 각자 try/catch를 써서 오류 포맷이 갈라진다. 제안 — 둘 다 packages/lib/에 둔다 (U1 승인 대상).

F-3 · design/ §5.1·§6.2의 Stage 체계가 낡았다

배지표는 5_READY_FOR_DEPLOY·7_DEV_SERVER_TEST·8_COMPLETED·0_QUEUED를, Flow는 ① → ② → ③ → ④ → ⑤ → ⑦ → ⑧을 쓴다. D-05·R-04가 없앤 값들이고 contracts/stage.ts에도 없다. 0_QUEUED는 대기 큐 자체가 사라졌으므로 더더욱 성립하지 않는다. 해소 — Q5=A에 따라 이미 1→2→3→4→9로 갱신된 08-sr-registration-ui.md를 따른다. design/ 문서는 수정하지 않는다 — 정리 여부는 사용자 판단이며 C-1과 함께 남긴다.

상태배지확정 근거
1_REGISTERED ~ 4_DEV_IN_PROGRESSaccentdesign §5.1 “진행 중” 행의 의미를 현 Stage 집합에 적용
9_COMPLETEsuccessdesign §5.1 8_COMPLETED 행의 계승
X_STOPPEDwarningdesign §5.1 그대로
X_FAILEDerrordesign §5.1 그대로

따라서 대시보드 카드는 진행 / 완료 / 실패 3장이다. design/ §4.2의 “대기” 카드는 0_QUEUED가 없으므로 만들지 않는다.

F-5 · 배치2 전제 — chart에 S3_*가 없다

10-k8s-infrastructure.md §7은 S3_ENDPOINT·S3_BUCKET·S3_ACCESS_KEY·S3_SECRET_KEY를 필수로 정의하지만 charts/.../portal.yaml에는 SDLC_IMAGE_SIGNING_SECRET만 있다. US-U2-07에 필요하며 chart는 U1 소유이므로 Step 17에서 승인 항목으로 처리한다.

F-6 · 웹 터미널은 되살리지 않는다 (기록만)

08-sr-registration-ui.md §6.5와 design/ §4.4는 웹 터미널(엔드포인트 5종, K8s pods/exec)을 규정하지만 requirements.md의 FR에도 stories.md의 어느 스토리에도 없다. Requirements Analysis에서 이미 빠진 것으로 보이며 U2가 임의로 되살리지 않는다. “재개발 / 테스트 진행” 버튼도 같다 — 그 버튼들은 존재하지 않는 Stage 7에 걸려 있다. U2는 §6.3대로 “중지” 버튼 하나만 만든다.

덤으로 잡은 빌드 파손 지점

U1이 만든 apps/portal/src/app/page.tsx가 /를 차지하고 있다. 대시보드가 (dashboard)/page.tsx로 들어가면 같은 경로를 해석하는 파일이 둘이 되어 빌드가 깨진다. Step 11에서 삭제·대체하고, U1이 만든 파일이므로 PR 설명에 명시한다.

경계방향U2에서의 의미
B-1U2 → U3SdlcRequestFactory·PodPort — stub으로 착수, U3 T1·T2 완료 후 교체

B-4Pod → U2이미지 업로드 엔드포인트 (배치2)

stub 2건에는 지키지 않으면 설계가 무너지는 조건이 있다

① SdlcRequestFactoryStub은 metadata에 channelTypes·autoMergeAllowed가 각인된 객체를 반환해야 한다. 각인 없이 반환하면 정책을 다시 판정하는 코드가 생겨 AD-3이 무력화된다.
② StateMachineStub은 Reader만 구현한다. advance·setSubStage를 만들면 B-3의 읽기 전용 경계가 stub 단계에서 이미 깨진다.
