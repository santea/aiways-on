# 승인 게이트 신설 결정 질문 (GAP-04 / GAP-05)

**작성**: 2026-09-08 · Requirements Analysis 재방문 (User Stories v2 보강에서 도출)
**결정 대상**: 요구사항 정의서 · 상세 설계서에 대한 **인간 승인 게이트**를 신설할 것인가

---

## 1. 무엇이 문제인가

내러티브는 인간 승인을 **2회** 전제한다.

> "요구사항이 충분히 구체화되면 AI Agent가 요구사항 정의서를 작성하고 **시스템 사용자(A)의 확인 및 승인**을 받는다."
> "AI Agent는 이 내용을 기반으로 상세 설계서를 작성하고, **확정된 설계에 따라** 실제 개발을 진행한다."

그런데 현행 명세의 실제 게이트는 **목업 확정 1회뿐**이다.

| 지점 | 현행 진행 조건 | 사람이 막을 수 있는가 |
|------|--------------|---------------------|
| 요구사항 인터뷰 종료 | AI Agent의 `end` 판정 (Pod 출력 텍스트 기반) | ❌ 아니오 |
| **UI 목업 확정** | `mockupConfirmed` — 사용자가 "이대로 좋다"고 말해야 `true` | ✅ **예** (유일한 게이트) |
| 요구사항 정의서 게시 → `2→3` | 게시 직후 자동 전이 | ❌ 아니오 |
| 상세 설계서 게시 → 개발 시작 | 게시 직후 자동 전이 | ❌ 아니오 |
| `4→9` PR 생성 → merge | `autoPrMerge` 설정값 | ⚠️ **설정에 따라 다름** |

### 실제로 벌어질 수 있는 일

`is_ui=false`인 repo(백엔드·배치 등)는 목업 단계가 `NO_UI`로 즉시 종료되므로 **유일한 게이트마저 없다**.
여기에 `autoPrMerge=true`가 겹치면:

```
SR 접수 → AI 인터뷰 → AI가 end 판정 → 정의서 게시 → 자동 전이
        → AI 설계 인터뷰 → 설계서 게시 → 자동 전이
        → AI 개발·QA·리뷰 → PR 생성 → 자동 squash merge → main
```

**사람의 명시적 승인이 0회**인 경로가 성립한다.

> 참고 — `incident`·`improvement` 프로파일은 요구사항·설계 단계를 **구조적으로 건너뛰므로**(`dev` 채널 1개만 사용)
> 이 게이트는 `feature` 프로파일에만 존재할 수 있다. 프로파일 적용 범위는 질문 대상이 아니다.

## 2. 신설할 경우 무엇이 바뀌는가 (영향 분석)

### 재사용 가능한 기존 자산 — 새로 만들 것이 많지 않다

| 필요한 것 | 이미 있는 것 | 추가 작업 |
|----------|------------|----------|
| 사용자 응답 대기 | `sdlc_feedback_polls` (active·CAS dedup) | 없음 — 그대로 사용 |
| 응답 요청 게시 | `POST /requests/{id}/feedback-request` | 없음 |
| 독촉 | `nudgeMailSent` · `lastMailSentAt` · `stage-done-mail` | 없음 |
| 확정 신호 판정 | 목업의 `mockupConfirmed` 판정 Agent | **판정 프롬프트 1~2개 추가** |
| 재발화 루프 | Workflow B의 목업 서브루프 | **동형 서브루프 1~2개 추가** |

**즉, 목업 확정 루프와 같은 구조를 요구사항 정의서·설계서에 복제하는 일이다.** 새로운 메커니즘 발명이 아니다.

### 영향 받는 산출물

| 대상 | 변경 내용 |
|------|----------|
| `requirements.md` | FR 신설 (요구사항 승인 게이트 / 설계 승인 게이트) — 현재 45 FR 중 해당 항목 없음 |
| `stories.md` | `US-U3-21` · `US-U3-23`에 인수 조건 추가 (승인 대기·거부·재작업 경로) |
| U3 (진행) | n8n Workflow B 서브루프, 확정 신호 판정 프롬프트 |
| U2 (관리) | **Q2에서 B·D를 고를 때만** — `/requests/[id]` 승인 UI + 승인 API + 감사 기록 |
| 상태 머신 | 신규 Stage 추가 **없음** — `2`·`3` 단계 내부의 대기 루프로 처리 (Stage enum 7개 유지, D-05·R-04 무영향) |

### 신설하지 않을 경우의 대안 안전장치 (이미 존재)

- `autoPrMerge` 기본값 **false** (`04-db-schema.md:282`) — 켜지 않으면 PR 리뷰가 최종 게이트
- `US-U2-10` — repo별 정책을 admin이 통제
- 실패 채널 미아카이브(NFR-08) — 사후 추적 창구는 남음

## 3. 질문

## Question 1
승인 게이트를 어디에 신설할 것인가?

A) **두 곳 모두 신설** — 요구사항 정의서(요청자 A 승인) + 상세 설계서(OWNER B 승인). 내러티브 원안 그대로

B) **요구사항 정의서만** — 잘못된 요구사항이 가장 비싼 오류이므로 입구만 막는다. 설계는 OWNER가 `design` 채널에서 상시 개입 가능하므로 별도 게이트 없이 진행

C) **상세 설계서만** — 코드에 직접 영향을 주는 마지막 지점만 막는다. 요구사항 단계는 목업 확정으로 갈음

D) **신설하지 않음** — 현행 유지. `autoPrMerge=false` 기본값과 PR 리뷰를 최종 게이트로 삼는다

E) **조건부 신설** — 평소에는 현행대로 진행하되, `autoPrMerge=true`인 repo에서만 두 게이트를 강제한다 (자동 머지를 켠 repo만 사람 확인을 요구)

X) Other (please describe after [Answer]: tag below)

[Answer]: X - 요구사항 게이트는 OWNER B가 portal통해 승인, 설계 게이트는 승인 없이 자동으로 다음 단계로 진행

## Question 2
승인을 어떤 방식으로 받을 것인가? *(Question 1에서 A·B·C·E를 선택한 경우에만 해당)*

A) **채널 확정 마커** — 목업 루프와 동일한 구조. 채널에 정의서/설계서를 게시하고 사용자가 "확정한다"고 답하면 판정 Agent가 `===REQUIREMENTS_CONFIRMED===` / `===DESIGN_CONFIRMED===`를 출력. 기존 feedback poll·독촉 메일을 그대로 재사용하므로 **추가 비용이 가장 낮다**

B) **Portal UI 승인 버튼** — `/requests/[id]`에 승인/반려 버튼. 누가 언제 승인했는지가 `audit_events`에 확정적으로 남는다. U2에 화면·API 추가 필요

C) **GitHub Issue 기반** — Issue comment(`/approve`) 또는 reaction으로 승인. 이미 정의서·설계서 전문이 Issue에 게시되므로 같은 자리에서 처리

D) **A + B 병행** — 채널이 기본 경로, 웹 승인 버튼은 대체 경로. 감사 기록은 양쪽 모두 남긴다

X) Other (please describe after [Answer]: tag below)

[Answer]: B

## Question 3
승인자가 응답하지 않으면 어떻게 할 것인가?

A) **무기한 대기 (fail-closed)** — 승인 없이는 절대 진행하지 않는다. SR이 영구히 멈출 수 있음

B) **독촉 후 무기한 대기** — 기존 `nudgeMailSent` 독촉을 N회 발송하되, 끝까지 승인을 기다린다

C) **타임아웃 후 자동 진행 (fail-open)** — 지정 시간(예: 24시간) 무응답 시 승인으로 간주하고 진행. 게이트가 있으나 사실상 지연 장치로 동작

D) **타임아웃 후 `X_STOPPED` 종료** — 지정 시간 무응답 시 SR을 중지하고 사람이 다시 시작하게 한다. Pod 자원이 회수됨

X) Other (please describe after [Answer]: tag below)

[Answer]: A

## Question 4
누가 승인할 수 있는가?

A) **채널 참여자 누구나** — 현행 피드백 처리와 동일. 발화자 신원을 따로 검증하지 않는다 (구현 비용 최소)

B) **역할별 지정** — 요구사항 게이트는 SR 등록자(요청자 A)만, 설계 게이트는 해당 repo의 OWNER만 승인 가능

C) **역할별 지정 + admin 대리 승인** — B에 더해 `admin`은 언제든 대리 승인할 수 있다 (담당자 부재 시 파이프라인 정지 방지)
