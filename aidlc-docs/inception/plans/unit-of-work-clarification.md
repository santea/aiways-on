## 모호성 1 — Q4 "간소화"의 대상이 무엇인지

**답변**: `x - 가능한 일정 안에서 진행되도록 간소화`

**왜 명확화가 필요한가**: "간소화"의 대상이 셋 중 어느 것인지에 따라 결과가 정반대가 됩니다.

- **테스트 더블을 간소화**한다면 → 병렬 착수는 유지되고 테스트 깊이만 얕아짐
- **TDD 자체를 간소화**한다면 → **D-20(TDD 강제 + CI 커버리지 게이트)의 부분 철회**에 해당하고,
  Q13=A로 확정한 결정을 바꾸는 것이라 기록이 필요합니다
- **병렬 착수를 간소화**한다면 → U4·U5가 U3 완료를 기다리게 되어 **일정이 오히려 늘어납니다**
  (Q4의 B안. "일정 안에서"라는 의도와 반대 방향)

셋 중 무엇인지는 유닛의 완료 정의(DoD)와 착수 순서를 결정하므로 추측으로 넘어갈 수 없습니다.

### Clarification Question 1
Q4의 "간소화"는 무엇을 간소화한다는 뜻입니까?

A) **테스트 더블은 쓰되 가볍게** — 각 유닛은 손으로 만든 최소 stub(고정값 반환)으로 착수하고, 별도의 계약 테스트 스위트는 만들지 않는다. 통합 시 실제 구현으로 교체하고 통합 테스트로만 검증. **TDD와 커버리지 게이트는 그대로 유지** *(권장 — 병렬 착수를 지키면서 Q4=A에서 무거운 부분(계약 테스트 스위트)만 덜어냄. D-20을 건드리지 않음)*

B) **경계를 넘는 부분은 TDD 예외** — 다른 유닛에 의존하는 코드는 테스트 없이 먼저 작성하고 통합 후에 테스트를 붙인다. 커버리지 게이트는 경계 코드에 한해 완화. **D-20의 부분 예외를 명시적으로 기록**

C) **의존을 끊어서 간소화** — U4·U5·U2가 `SdlcRequestFactory`를 직접 호출하지 않고, 각자 SR 행을 만든 뒤 U3가 나중에 정책을 각인. 테스트 더블 자체가 불필요해짐 *(주의: AD-3의 "Factory 우회 금지" 규약과 충돌하며, incident 자동머지 금지 규칙이 깨질 수 있음)*

D) **A와 B 둘 다** — 최소 stub을 쓰되, 그래도 막히는 경계 코드는 TDD 예외로 처리

## 모순 1 — Q9=C가 명세의 디렉토리 구조와 충돌

**답변**: `C - api 규약과 공통 lib 같이 중복되는 내용만 공유`

**충돌 내용**: `requirements/00-overview.md` §5는 디렉토리 구조를 **단일 Next.js 앱 + 평면 `src/`**
로 명시하고 있습니다. 워크스페이스 패키지 분리 구조가 아닙니다.

```
aiways-on/
├── src/
│   ├── app/          # Next.js App Router
│   ├── lib/          # sdlc/ · adapters/
│   ├── db/schema/    # Drizzle
│   └── auth.ts
├── drizzle/  n8n/  sdlc-pod-runner/  sdlc-memory-mcp/  sdlc-slack-gateway/  docs/
```

`requirements/`는 **SSOT(단일 진실 공급원)** 이고, 앞선 결정(Q5=명세 우선)에 따라 참고자산이
아니라 명세가 이깁니다. Q9=C는 이 구조를 대체하는 변경입니다.

**추가로 — 답변 문장과 선택지가 서로 다른 것을 가리킵니다.**

- 선택지 C의 본문: "**유닛별 패키지 완전 분리**" → 패키지 6개 이상 + 앱은 껍데기
- 답변에 덧붙인 문장: "**중복되는 내용만 공유**" → 공유 패키지 2개 정도 + 나머지는 앱 안에

두 번째 문장은 오히려 **A에 공유 패키지를 얹은 형태**에 가깝습니다. 실제로 하려는 것이 어느
쪽인지에 따라 6명의 작업 방식과 빌드 구성이 크게 달라집니다.

**일정과의 관계도 함께 봐야 합니다.** Q4에서 "일정 안에서 진행되도록 간소화"를 택하셨는데,
Q9=C(완전 분리)는 제가 선택지에 "2일 일정에 부담"이라고 표시한 가장 무거운 안입니다.
Next.js App Router는 라우트 파일이 앱 하나에 모여야 하므로, 유닛별 패키지로 완전히 나눠도
`src/app/**`은 결국 공유됩니다 — 경계가 가장 필요한 화면 부분이 패키지 분리로는 안 나뉩니다.

### Clarification Question 2
코드 조직을 어느 형태로 확정할까요?

A) **경량형 — 앱 1개 + 공유 패키지 2개** — `apps/portal/src/features/{unit}/`에 유닛별 로직, `src/app/({unit})/`에 라우트 그룹. 여기에 `packages/contracts`(API 규약·공유 타입)와 `packages/lib`(공통 유틸)만 별도 패키지로 뺀다. 답변의 "중복되는 내용만 공유"를 그대로 구현한 형태 *(권장 — 답변 문장의 의도와 일치하고, 명세 §5 구조에서 벗어나는 폭이 가장 작으며, Q5의 CODEOWNERS는 `features/`·`app/` 경로에 걸어 동일하게 동작함)*

B) **완전형 — 유닛별 패키지 분리** — `packages/u1-shared`·`u2-core-mgmt`·`u3-core-run`·`u4-incident`·`u5-improvement`·`u6-memory` + `apps/portal`. 라우트 파일은 앱에 남고 각 패키지의 페이지 컴포넌트를 얇게 재수출. 경계는 가장 강하지만 빌드 구성·초기 셋업 비용이 큼 (선택지 C의 원래 의미)

C) **명세 §5 그대로 + 유닛 디렉토리만 추가** — 워크스페이스 없이 `src/features/{unit}/`만 도입. 공유는 `src/lib/`이 담당. 명세와 100% 일치하고 가장 가벼움 (원래 Q9의 A안)

D) **B로 하되 범위 축소** — 독립 배포 서비스(Pod Runner·Gateway·MCP)만 별도 패키지로 두고, Portal 안의 5유닛은 디렉토리로만 분리. 명세 §5가 이미 이 서비스들을 최상위 디렉토리로 두고 있어 자연스러움

### Clarification Question 3
공유 영역(패키지 또는 `src/lib`)에 무엇을 넣을까요?

A) **타입·계약만** — `SharedTypes`(Stage·ChannelType·DTO·Port 3종·Factory 시그니처)만 공유. `AuthGuard`·스키마·디자인 토큰은 앱 안 U1 디렉토리에 두고 import로 사용

C) **타입 + 스키마** — 계약과 데이터 정의는 공유, 실행 코드(`AuthGuard`)와 UI(디자인 토큰)는 앱 안에
