AD-1

순환 의존을 타입 의존으로 바꿔 끊었다

상태머신(U3)이 4→9 전이에서 PR을 만들려면 GitHub 어댑터(U2)가 필요하고, 접수(U2)는 프로비저닝(U3)이 필요했다. 양방향 구현 의존은 병렬 개발에서 교착이 된다.

AD-3 · 가장 중요한 결정

규칙을 코드가 아니라 데이터에 각인했다

명세에는 "장애(incident) SR은 repo 설정이 자동머지 허용이어도 머지하지 않는다"는 조항이 있다. 이 규칙이 U3 상태머신의 조건문으로만 존재하면, U4 담당자가 조항을 모르는 순간 장애 패치가 사람 확인 없이 머지된다.

답변을 그대로 받지 않고 한 번 되물은 지점

원래 답변은 "유닛별 생성 함수 + 단일 공통 validator"였다. 그런데 자동머지 규칙이 적용되는 시점은 SR 생성이 아니라 4 → 9 전이다. validator가 생성 입력만 검증하면 규칙은 여전히 U3 코드에만 남는다. 이 공백을 확인받아 validator가 정책까지 결정해 각인하는 형태로 확정했다.

Decisions

설계 결정 6건

AD-1S-1 해소

Port 인터페이스를 U1로

GitHubPort · MessagingPort · PodPort 3종을 U1이 정의하고 구현은 각 유닛이 소유. 순환 제거.

AD-2S-2 해소

인증 단일 소유

GitHub OAuth + 서버간 인증 4종을 AuthGuard 하나가 제공. 나머지 5개 유닛은 소비만 — 유닛별 강도 편차를 막는다.

AD-3S-3 해소

정책 각인

단일 validator가 채널 개수와 자동머지 허용을 결정해 SR에 각인. 전이 로직은 읽기만 한다.

AD-4S-4 해소

인터페이스 소유자 1명

경계 9건의 실체는 7개 인터페이스. 타입은 U1 공유 패키지에 두되 수정 권한은 소유자만.

AD-5S-5 해소

ConfigMap 키 하나

MCP 주입은 U1·U3·U6 3자 조율. 합의할 것은 sdlc-endpoints.memoryMcpUrl 키 이름 하나, 값은 Service DNS.

AD-6

경계 규약 명문화

타입으로 표현되는 계약은 CI가 이미 잡는다. 표현 안 되는 규약(호출 순서·멱등 책임)을 B-1~B-7로 적어 리뷰에서 대조.

Slack Gateway를 따로 뗀 이유

Portal은 replicas: 2+다. Socket Mode를 Portal에 내장하면 replica 수만큼 중복 수신되어 같은 피드백이 두 번 처리된다. 장수명 연결만 단일 replica 전용 Pod로 분리해 Portal의 무상태성을 지킨다.

Impact

착수 순서가 바뀌었다

차단 구간이 줄었다

이전에는 U1이 끝나야 나머지 5명이 착수할 수 있었다. 이제는 U1의 인터페이스 선언만 끝나면 된다 — U3는 Port 선언만 있으면 전이 로직을 짜기 시작하고, U4·U5는 Factory 시그니처만 확정되면 착수한다. 2일 일정에서 이 차이가 크다.

시점필요한 것
U3 착수공유 타입의 Port 인터페이스 선언만 — 구현 불필요
U4 · U5 착수SdlcRequestFactory 시그니처만 확정 — 구현은 진행 중이어도 됨
U2 · U3 통합GitHubAdapter가 GitHubPort를 구현하는지 typecheck
B-6 연결가장 늦어도 됨 — U5 · U6 각자 완성 후 마지막에

Units Generation으로 넘길 것

U3 부하 — 컴포넌트 9개(전체의 29%)에 독립 배포 3개. 재분배 또는 2인 배정 검토. 완화 후보는 n8n 워크플로우로, 배포 이후 착수라 시간축에서 분리할 수 있다.
Portal 공존 — 5개 유닛이 한 서비스에 코드를 넣으므로 디렉토리 경계 규약이 필요하다.
