Key Calls

이번 단계에서 갈린 세 가지

상태 머신은 명세를 따른다 — 참고자산의 구 체계는 버린다

기존 n8n 워크플로우와 claude-global.md는 Advance to 5, "보고서 작성 (Stage 7)"처럼 구 stage 번호를 쓴다. 명세는 Stage 5–8을 enum 값 없는 미사용 예약으로 두고 정상 경로를 1 → 2 → 3 → 4 → 9_COMPLETE로 규정한다. 명세를 채택했고, n8n은 번호를 재매핑해 신규 작성한다. 참고자산의 구 번호가 코드에 새어 들어오는 것이 리스크 R-04다.

범위·깊이·일정을 모두 유지한다 — 바이브코딩 생산성이 근거

12 person-day(6명×2일)로 명세 15,033줄을 TDD로 완주하는 것은 통상 공수 산정으로는 불가능하다는 우려를 제기했고, 두 차례 "바이브코딩으로 2일 내 가능"으로 확인받았다. 사용자 결정으로 수용해 전체 범위·전체 깊이로 진행한다. 이 가정이 어긋나면 가장 먼저 조정할 후보는 범위이며, 그 판단은 사용자가 한다.

구조적 병목 두 곳이 이미 보인다

U1이 나머지 5명 전원을 차단한다 — 스키마·타입·인증이 없으면 아무도 시작할 수 없다. 그리고 U3가 명세의 27%를 혼자 진다. 2일 일정에서 둘 다 치명적이므로, Units Generation에서 U1 인터페이스 우선 산출과 U3 재분배를 설계한다.

Quality Gates

확장 규칙 준수

Security Baseline

전체 적용

OWASP Top 10 전체. SECURITY-01~15 전부 blocking이며 비기능 요구사항 NFR-10~20에 매핑했다.

Resiliency Baseline

예외 2건

RESILIENCY-01~15 적용. 단 아래 2건은 사용자 승인 예외로, 이후 모든 단계 준수 요약에 계속 표시된다.

Property-Based Testing

부분 적용

순수 함수와 직렬화 왕복에만. 대상 후보는 advance(), 멱등키 생성, DTO 직렬화, 채널명 규칙.

사용자 승인 예외 — 은폐하지 않고 계속 표시

RESILIENCY-14 복원력 테스트 생략(설계 원칙만 준수) · RESILIENCY-15 운영 장애대응 프로세스 v2 연기. 둘 다 2일 일정을 이유로 사용자가 제시된 선택지에서 명시적으로 선택했다. 기본값이 blocking인 규칙이므로 예외임을 계속 드러낸다.

혼동 주의: RESILIENCY-15의 "v2 연기"는 팀이 AIways-On 장애에 대응하는 절차를 미룬다는 뜻이다. 제품 기능인 장애대응 Agent(U4)는 D-01에 따라 v1 범위에 그대로 포함된다.

Open Decision

다음에 정할 것

User Stories 단계를 실행할까?

실행 근거 — 사용자 대면 라우트 18개, 다중 페르소나(요청자·개발자·운영자·admin), 6인 협업으로 공통 이해가 필요한 조건. AI-DLC 판정 기준으로는 실행 권장 대상이다.

생략 근거 — 2일 일정. 그리고 design/ 문서가 이미 화면별 표시 정보와 권한 매트릭스를 정의해 스토리가 더할 정보가 제한적이다.

생략하면 Workflow Planning → Units Generation으로 직행해 6유닛 분할을 확정하고 바로 Construction에 들어간다.
