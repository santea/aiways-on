**검증**: 각 페르소나의 권한 범위를 `design/웹화면-디자인-요구사항_v1.md` §8 권한 매트릭스와 교차 검증함
**v2 보강(2026-09-08)**: 비즈니스 내러티브의 액터 A·B 매핑, 정량 기준선, OWNER 책임 분해를 문서 하단 「v2 보강」에 추가함

## 사람 페르소나

### P1 · 요청자 (Requester) — 내러티브의 **A · 시스템 사용자**

| 항목 | 내용 |
|------|------|
| **역할** | 현업 담당자 / 기획자. 개발이 필요한 일을 가진 사람 |
| **기술 수준** | 낮음~중간. Git·K8s를 모를 수 있고, 요구사항을 개발자 언어로 정리하지 못함 |
| **권한** | `user` — 본인이 등록한 SR만 조회 가능 |
| **주 화면** | `/register`, `/`, `/requests/[id]` |
| **주요 접점** | Slack `sr-{no}-requirements` 채널에서 AI와 인터뷰, 목업 확정 |

**목표**
- 막연한 요구를 말로 설명하고, 시스템이 알아서 정리해 주기를 원함
- 내 요청이 지금 어느 단계인지, 언제 끝나는지 알고 싶음
- 개발 결과가 내가 생각한 화면과 같은지 **개발 전에** 확인하고 싶음

**불만 (Pain Points)**
- 요구사항을 문서로 쓰라고 하면 무엇을 써야 할지 모름
- 개발이 끝난 뒤에야 "생각한 것과 다르다"는 걸 알게 됨
- 진행 상황을 물어보려면 매번 개발자를 찾아야 함

**시스템이 이 사람에게 하는 약속**
소크라테스식 인터뷰(`sdlc:user-deep-interview`)로 요구사항을 대신 정리하고,
개발 전에 Before/After 목업을 보여 준다. 확정 신호(`===MOCKUP_CONFIRMED===`) 전까지 다음 단계로 넘어가지 않는다.

---

### P2 · 개발자 (Developer) — 내러티브의 **B · 시스템 OWNER** (기술 판단 축)

| 항목 | 내용 |
|------|------|
| **역할** | SR을 실제로 검토하고, AI 산출물의 품질을 책임지는 사람 |
| **기술 수준** | 높음. Git·PR·코드리뷰가 일상 |
| **권한** | `user` — 본인 SR 조회. repo 소유 여부와 무관하게 채널에서는 참여 |
| **주 화면** | `/requests/[id]`, `/incidents/[id]`, `/improvements/[id]`, `/memory` |
| **주요 접점** | Slack `sr-{no}-design` / `-dev` 채널, GitHub Issue·PR |

**목표**
- AI가 만든 설계와 코드가 우리 규정에 맞는지 확인하고, 아니면 되돌리고 싶음
- 어느 substage(`dev`/`qa`/`code_review`/`security_review`)에서 무엇이 실패했는지 알고 싶음
- 로컬 Claude Code가 우리 팀 개발 규정을 알고 있기를 원함

**불만**
- AI가 만든 PR을 통째로 읽어야 하고, 어디를 봐야 할지 모름
- 실패했는데 왜 실패했는지 로그를 뒤져야 함
- 사람마다 코딩 규칙이 달라 리뷰에서 매번 같은 지적을 반복함

**시스템이 이 사람에게 하는 약속**
DevSubStage 4종을 분리해 어디서 멈췄는지 정확히 보여 준다.
실패한 채널을 아카이브하지 않고 실패 원인을 게시해 후속 논의 창구로 남긴다(NFR-08).
개발 규정을 MCP로 로컬 Claude Code에 주입한다.

---

### P3 · 운영자 / Admin — 내러티브의 **B · 시스템 OWNER** (플랫폼 권한 축)

| 항목 | 내용 |
|------|------|
| **역할** | 시스템 전체를 관리. GitHub Org·Repo·자격증명·템플릿·토큰을 다룸 |
| **기술 수준** | 높음. K8s·GitHub App·Slack App 설정 가능 |
| **권한** | `admin` — **전체 SR 조회** + 관리 화면 6종 + 장애 승격·종결 + finding 승격 확정 |
| **주 화면** | `/admin/*` 6종, `/incidents/inject`, 모든 목록 화면 |

**목표**
- 어떤 repo에 SDLC를 열어 줄지 통제하고 싶음
- 장애가 진짜인지 판단하고 incident SR로 승격할지 결정하고 싶음
- 자체개선 finding 중 무엇을 실제 SR로 만들지 최종 확정하고 싶음
- 파이프라인이 고장났을 때 개입할 지점이 있기를 원함

**불만**
- 자동화가 폭주해 원치 않는 PR이 쌓이는 것이 두려움
- 실패한 SR이 조용히 사라지면 원인을 추적할 수 없음
- Secret이 DB에 평문으로 남는 것을 용납할 수 없음

**시스템이 이 사람에게 하는 약속**
`SDLC_INCIDENT_ENABLED` / `SDLC_IMPROVEMENT_ENABLED` fail-closed 플래그로 접수 자체를 차단할 수 있다.
보상 트랜잭션은 전체 삭제가 아니라 단계별 보상 + 운영자 개입 지점을 남긴다.
Secret은 `secret_refs` 암호화 참조로만 저장한다(NFR-10).

### P4 · 사내 개발자 (MCP 소비자)

| 항목 | 내용 |
|------|------|
| **역할** | AIways-On 파이프라인을 쓰지 않고, 자기 로컬에서 Claude Code로 개발하는 사내 개발자 |
| **기술 수준** | 높음 |
| **권한** | `user` + 발급받은 MCP 토큰(`sdlcmem_*`) |
| **주 접점** | 로컬 Claude Code ↔ `sdlc-memory-mcp` (Streamable HTTP :58002). 웹은 `/memory` 조회만 |

**목표**
- 팀 개발 규정을 매번 문서에서 찾지 않고 Claude Code가 알아서 참조하기를 원함
- 규정이 바뀌면 자동으로 최신 내용이 반영되기를 원함

**불만**
- 규정 문서가 어디 있는지 모르고, 있어도 읽지 않음
- 규정이 바뀐 걸 아무도 알려주지 않음

**시스템이 이 사람에게 하는 약속**
MCP 서버를 통해 규정을 Claude Code 컨텍스트에 직접 공급한다. 토큰은 발급·폐기 가능하다.

### S1 · n8n 오케스트레이터

| 항목 | 내용 |
|------|------|
| **책임** | 단계 진행 권한의 **유일한 소유자**. Workflow A(intake) / B(run-callback) / C(logging) |
| **아는 것** | 현재 stage·substage, 어떤 프롬프트를 어느 Pod에 보낼지 |
| **모르는 것** | 파이프라인 프로파일(`feature`/`incident`/`improvement`) — Portal이 판정 |
| **경계** | Pod에 stage를 알려주지 않는다. Pod의 출력 텍스트만 보고 판정한다 |

**목표**
- Pod가 낸 확정 신호를 정확히 판정해 다음 단계를 발화하고 싶음
- 고아 세션을 감지해 예산 한도 내에서 재개하고 싶음

**핵심 제약**
Pod의 `/run` 종료 출력 텍스트만 볼 수 있고 사용자 원문은 보지 못한다.
따라서 판정은 정확한 마커 문자열에 의존한다.

### S2 · SDLC Pod (Claude Code 실행기)

| 항목 | 내용 |
|------|------|
| **책임** | 격리 K8s Pod 안에서 Claude Code 실행. clone·run·commit·push |
| **아는 것** | 자기 워크스페이스(`/workspaces/session`), 방금 받은 프롬프트 |
| **모르는 것** | **stage를 모르고, 알 필요도 없다** |
| **경계** | 자의로 다음 단계를 시작하지 않는다. PR 생성·merge를 하지 않는다(Portal 담당) |

**목표**
- 지시받은 작업만 정확히 수행하고, 결과와 확정 신호만 출력하고 종료하고 싶음
- 메모리 한계 안에서 죽지 않고 완주하고 싶음 (OOM 방지)

**핵심 제약**
Stage 4는 `dev`/`qa`/`code_review`/`security_review` 4개의 독립 `/run`으로 나뉜다.
하나의 `/run` 안에서 다음 substage를 스스로 잇지 않는다.

# v2 보강 — 비즈니스 내러티브 정렬 (2026-09-08)

> **보강 근거**: 사용자가 제공한 AIways-On 내러티브(요청 배경·A/B 액터 정의·SDLC 진행 예시·MCP 활용·장애 대응·지속 개선·메신저 기반 운영).
> v1 페르소나는 *명세와 화면 권한*에서 도출됐고, v2는 여기에 **왜 이 사람이 이 일을 하는가(비즈니스 기준선)** 를 붙인다.

## 비즈니스 기준선 (AS-IS) — 페르소나 불만의 정량 근거

| 지표 | 현재 값 | 누구의 시간인가 | AIways-On가 겨냥하는 지점 |
|------|--------|----------------|--------------------------|
| 시스템당 개선 요청 접수량 | **약 20건 / 월** | P1이 만들고 P2가 받는다 | 접수 창구를 메신저로 옮겨 등록 마찰 제거 |
| 요구사항 파악 (미팅·인터뷰) | **약 1일 / 건** | P2의 시간 | AI 인터뷰가 대신 수행 (US-U3-20) |
| 실제 개발 | **2~3일 / 건** | P2의 시간 | 바이브 코딩 자동 실행 (US-U3-09, Stage 4) |
| 설계·검토·테스트·배포 준비 포함 **총 리드타임** | **약 1주 / 건** | P1의 대기 시간 | 전 구간을 파이프라인으로 연결 |

> ⚠️ 이 수치는 **내러티브에서 온 관찰값**이며 `requirements.md`의 FR/NFR로 편입되어 있지 않다.
> 리드타임을 실제로 계측·리포팅하는 기능은 현재 명세에 없다 — `stories.md` **GAP-07** 참조.

## 내러티브 액터 ↔ 페르소나 매핑

| 내러티브 | 대응 페르소나 | 매핑 근거 | 주의 |
|----------|--------------|----------|------|
| **A · 시스템 사용자** | **P1 요청자** | 최초 요청자 · 요구사항 불명확 · 개발 비전문가 — 동일 정의 | 1:1 대응 |
| **B · 시스템 OWNER** | **P2 개발자 + P3 Admin** | 명세는 B의 권한을 **repo 소유자의 기술 판단(P2)** 과 **플랫폼 설정 권한(P3)** 으로 분리한다 | ⚠️ **1:2 분해**. 내러티브의 "B가 판단"은 시스템에서 두 사람의 권한으로 나뉜다 |
| (내러티브에 없음) | P4 사내 개발자 | MCP 소비자 — 파이프라인 밖에서 규정만 소비 | 내러티브의 "MCP 기반 바이브 코딩 지원"이 파이프라인 밖까지 확장된 형태 |

### B의 책임이 P2/P3로 갈라지는 지점 — 착수 전 확인 필요

| 내러티브가 B에게 준 책임 | 시스템에서 실제 수행자 | 근거 |
|------------------------|---------------------|------|
| 기술 인터뷰 상대 (설계 결정) | **P2** — Stage 3 `design` 채널 | US-U3-22 |
| 상세 설계서 확인 | **P2** | US-U3-23 |
| PR 검토·머지 | **P2** — GitHub에서 수행 | US-U2-09 |
| **자동 머지 허용 조건 사전 설정** | **P3** — `/admin/repos`의 `autoPrMerge` 토글 | US-U2-10 |
| 데이터 노출 권한 범위 판단 | **P2** 설계 인터뷰에서 결정, **P3** 가 플랫폼 차원 강제 | US-U3-22, US-U1-02 |
| 운영 정책 (장애 승격·개선 승격) | **P3** | US-U4-02, US-U5-04 |

> **읽는 법**: 한 조직에서 P2와 P3가 같은 사람일 수 있다. 그러나 **권한은 분리해 설계**한다 —
> `autoPrMerge`를 켜는 행위는 "이 repo에서는 AI가 사람 없이 머지해도 된다"는 플랫폼 수준 결정이므로 P3의 것이다.

## P1 보강 — 요구사항 구체화 6축

내러티브의 엑셀 다운로드 예시가 요구하는 구체화 축이다. P1은 이 6가지를 **먼저 말하지 못하는 사람**이며,
시스템은 이것을 **되물어서** 채운다 (US-U3-20).

| 축 | 되묻는 질문 | 안 물으면 생기는 일 |
|----|-----------|-------------------|
| 대상 화면 | 어느 화면에 추가되는가 | 엉뚱한 화면에 개발 |
| 배치 위치 | 버튼이 화면 어디에 놓이는가 | 목업 단계에서 재작업 |
| Sheet 구성 | 어떤 Sheet가 필요한가 | 산출물 재작성 |
| Column 목록 | 각 Sheet에 어떤 컬럼이 들어가는가 | 데이터 쿼리 재설계 |
| 데이터 범위 | 어떤 기간·범위인가 | 성능 사고 |
| 검색조건 반영 | 화면 필터가 다운로드에 어떻게 반영되는가 | "내가 본 것과 다르다" |

## P2 보강 — 시스템 OWNER로서의 기술 결정 6항목

내러티브가 B에게 요구하는 설계 인터뷰 결정 항목이다 (US-U3-22의 인수 조건 원천).

| 결정 항목 | 왜 사람이 결정해야 하는가 |
|----------|------------------------|
| 수정 대상 파일·모듈 | AI가 코드만 보고 고르면 소유권 없는 모듈을 건드린다 |
| 아키텍처·개발 표준 준수 방법 | 표준은 코드에 안 쓰여 있다 → MCP `behavior` 규정으로 공급 (US-U6-08) |
| 데이터 조회·가공 방식 | 쿼리 한 줄이 운영 DB를 멈출 수 있다 |
| 데이터 노출 권한 범위 | 권한 판단은 비즈니스 결정이지 코드 결정이 아니다 |
| 기존 기능 회귀 차단 방법 | 영향 범위는 암묵지다 → MCP `system_profile`·`prohibition` |
| 테스트·검증 방식 | 무엇을 통과해야 "됐다"인지는 OWNER가 정한다 |

## v2에서 페르소나를 새로 만들지 않은 이유

내러티브의 A·B는 v1의 P1·P2·P3로 **완전히 커버된다**. 액터를 늘리면 권한 매트릭스(`design/` §8)와
어긋나므로, 새 페르소나 대신 **기존 페르소나에 책임과 정량 근거를 추가**하는 방식으로 보강했다.
