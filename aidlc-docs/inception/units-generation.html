착수를 막는 의존과, 나중에 연결되는 의존

컴포넌트 설계도는 U2와 U3 사이에 양방향 화살표를 보여준다. 그것을 그대로 착수 순서로 읽으면 두 유닛이 서로를 기다리는 것처럼 보이지만, 실제로 빌드를 막는 것은 import 하는 것뿐이다.

팀 제약이 문자 그대로 충족됐다

착수 조건은 “공용 유닛이 유일한 공통 선행인 의존 그래프”였다. U1을 그래프에서 지우면 나머지 5유닛 사이에 남는 간선은 0개다. PR #1 머지 후 5명은 서로를 기다리지 않는다.

발견 3건

1 · 워크스페이스가 새 위험을 만들었다

명세와 컴포넌트 설계는 Slack Gateway가 Portal과 코드·타입을 공유하지 않는다고 못 박는다 (replicas 1 고정 · 원본 봉투 그대로 전달). 그런데 워크스페이스에서는 packages/contracts를 import 하는 것이 한 줄이면 되는 일이 된다. 이 위험은 명세의 평면 구조에서는 없었고 UOW-9가 만든 것이다. 대응으로 Gateway에 워크스페이스 의존을 선언하지 않고, CI가 이를 검사하도록 U1의 품질 게이트에 넣었다.

2 · 명세 이탈을 되돌릴 수 있게 남겼다

요구사항 문서는 루트 src/ 단일 앱을 명시한다. UOW-9는 이를 apps/portal/src/ + packages/*로 바꾼다. 요구사항이 단일 진실 공급원이므로, 경로별 매핑과 되돌리는 방법을 문서에 함께 적었다. 유닛 경계는 features/ 디렉토리에 있어 되돌려도 깨지지 않는다.

3 · PBT 대상이 트랙을 가로질러 갈렸다

속성 기반 테스트 대상 3건이 전부 U3에 있는데, T1에 2건 · T3에 1건으로 나뉜다. 한쪽 트랙의 완료 정의에만 적으면 다른 쪽에서 누락되므로 두 트랙 모두의 DoD에 넣었다.
