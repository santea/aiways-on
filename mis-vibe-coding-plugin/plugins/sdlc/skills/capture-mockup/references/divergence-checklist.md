# Divergence 방지 체크리스트

"목업 ≠ 실제 개발 결과" 위험을 닫기 위한 대응표. capture-mockup 워크플로우의 근거.
단계 번호는 `capture-mockup-runner` agent의 워크플로우 §1~§12를 기준한다.

## 위험 → 대응

| # | 위험 원인 | 대응 방법 | 워크플로우 단계 |
|---|---|---|---|
| 1 | 목업이 실제 코드와 갈라짐 (HTML을 손으로 그림) | **실제 소스 편집 → 라이브 캡처(목업=코드)** → divergence 0 | §5 (edit all) |
| 2 | 개발 결과가 목표 스샷과 시각적으로 다름 | 목업이 곧 실제 코드 → 브랜치 이어받기, 기록용 재캡처만 | §12 (검증 루프) |
| 3 | 목업 소스 편집이 baseline/기준(feature) 브랜치에 새어 커밋·push됨 | `mockup/<featureName>` 격리 브랜치 + clean-tree 전제 + **push 금지** | §1 (브랜치 생성) |
| 4 | 다화면 진행 중 이전 확정 화면 유실 | **화면 확정마다 체크포인트 커밋** → §8 롤백은 `git revert --no-commit <대상 화면 커밋>`으로 **해당 화면만** 역적용(다른 화면 커밋 보존). `git restore .`는 커밋을 못 버리므로 사용하지 않음 | §5 (c) (체크포인트 커밋)·§8 |
| 5 | 거부 시 baseline 유실 | Before를 소스 편집 전 clean baseline에서 먼저 캡처 + 거부 시 `switch <baseline>` + `branch -D mockup/<featureName>`(브랜치째 삭제) 복원 | §1·§4·§10 |
| 6 | 인증 페이지라 캡처 실패 | 러너가 preAuth(OIDC 실제 로그인)/storageState로 처리 | §3 (로그인)·§4 (Before)·§5 (edit) |
| 7 | 반응형/뷰포트 차이로 스샷과 실제가 다름 | 캡처 viewport 고정 (기본 1920x1080) | 전 단계 |
| 8 | 폰트/에셋·HMR 반영 전 캡처되어 깨짐/stale | networkidle·HMR 대기 후 캡처 | §4·§6 (캡처 시) |
| 9 | 스샷 데이터가 메인 세션에 유입돼 컨텍스트 오염 | 러너가 캡처를 파일로만 저장, 메인엔 경로만 리턴 | 전 단계 |

## 검증 루프 판정 기준 (§12)

라이브 소스 편집 방식은 목업=실제 코드라 **기록용 재캡처**가 원칙이며 대개 그대로 통과한다.
아래 판정 기준은 그래도 어긋난 드문 경우의 fallback이다.

- **통과**: 개발 후 재캡처 스샷이 목표(after.png)와 레이아웃/색/컴포넌트 위치 일치 (기본)
- **불통과(드묾) → 재수정**: 구체적으로 무엇이 다른지 기술
  - "버튼이 좌측인데 목표는 우측"
  - "카드 배경색이 실제 토큰과 다름"
  - "간격이 목표보다 넓음"
- 일치할 때까지 반복. 목표 스샷이 단일 진실 공급원(SSOT).
